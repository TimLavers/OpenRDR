# Comment Requirements

A comment is a piece of text that the rules add to a case's interpretation. The report for a case is generated by the AI
from the comments its rules gave it.

Each comment is an `Attribute` of kind `COMMENT`, whose value for a case is the comment's text. A rule gives a comment
by assigning that attribute; the text itself is held as the attribute's definition, a `CommentTemplate`. So a comment
has a name, is referred to by identity rather than by its wording, and is shown in the Comments panel beside that name.

*(Before that change a comment was a `Conclusion`, a separate kind of thing with an id of its own, held in a conclusion
store and referenced by rules. This file was `conclusions.md`.)*

| Requirement          | Description                                                                                                    | Validation |
|----------------------|----------------------------------------------------------------------------------------------------------------|------------|
| Comment names        | Each comment has a name, being the name of its attribute; see [attributes.md](attributes.md).                  |            |
| One attribute a text | A comment text has one attribute: asking for a comment already in the knowledge base reuses it.                | Conc-4     |
| Text is fixed        | A comment's text does not change. Changing what a comment says is giving a different comment in its place.     |            |
| Comment variables    | A comment's text may contain variables that are replaced with case attribute values when the comment is shown. | Conc-5     |
| Text not blank       | The text of a comment cannot be blank. **Not currently enforced** (see below).                                 | Conc-2     |
| Maximum length       | There can be at most 2,048 characters in the text of a comment. **Not currently enforced** (see below).        | Conc-3     |

**The two validations above are not enforced by the current implementation.**
They were `require` checks on `Conclusion`, and went when that class did. No path currently refuses an overlong or blank
comment. They are recorded here as requirements still wanted, not as behaviour to rely on.

## Giving, removing and replacing comments

| Requirement       | Description                                                                                                                | Validation |
|-------------------|----------------------------------------------------------------------------------------------------------------------------|------------|
| Give a comment    | A rule gives a comment to the cases satisfying its conditions.                                                             |            |
| Remove a comment  | A refinement rule retracts the comment for the cases satisfying its conditions.                                            |            |
| Replace a comment | A refinement rule gives the replacement comment; the comment replaced is retracted, the leaf-most satisfied rule winning.  |            |
| Report            | The report for a case is made from the comments the rules gave it. See [ai_report_generation.md](ai_report_generation.md). |            |

## Inserting variables into a comment

A comment can include the current value of a case attribute by inserting that attribute's name delimited with braces,
e.g. `{TSH}`. When the comment is rendered for a case, each such variable is replaced with the attribute's latest value
in that case.

For example, the comment text:

> Your patient has a TSH of `{TSH}` mIU/L.

renders, for a case whose latest `TSH` value is `8.2`, as:

> Your patient has a TSH of 8.2 mIU/L.

The `{TSH}` form is what the user and the chatbot see. Within a comment's stored definition a variable is a positional
`${}` token with the attribute recorded beside it, so that renaming the attribute changes how the comment reads without
the comment having to be edited.

| Requirement             | Description                                                                                                     | Validation |
|-------------------------|-----------------------------------------------------------------------------------------------------------------|------------|
| Variable syntax         | A variable is written in a comment as an attribute name delimited with braces, e.g. `{TSH}`.                    | Conc-6     |
| Variable binding        | Each variable is bound to a case attribute; binding is by order of appearance in the comment text.              | Conc-7     |
| Value substitution      | When rendering a comment, each variable is replaced with the latest value of its attribute for that case.       | Conc-8     |
| Missing value marker    | If the attribute has no value (or no value for the case), `{<attribute name>: no value}` is shown in its place. | Conc-9     |
| Plain comment unchanged | A comment with no variables is rendered exactly as written.                                                     | Conc-10    |
| Renaming an attribute   | Renaming an attribute a comment refers to changes how the comment reads; the comment itself is unaffected.      |            |
