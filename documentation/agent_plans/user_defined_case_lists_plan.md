# User-defined case lists
Replace the single hardcoded "favourites" case list with support for any number of named, user-created case lists, per `documentation/requirements/user_defined_case_lists.md`, and retire the old favourites feature (`documentation/requirements/favourite_cases.md`).
## Current state
The favourites feature is threaded through every layer as a fixed, singular concept:
* `enum class CaseType { Cornerstone, Processed, Favourite }` (`common/src/main/kotlin/io/rippledown/model/CaseId.kt:5`) identifies which list a case belongs to. `CaseId.type` defaults to `Processed`.
* `CasesInfo` (`common/.../model/CasesInfo.kt`) carries a single `favouriteCaseIds: List<CaseId>`, and `count` only sums `caseIds` + `cornerstoneCaseIds` (favourites are never counted - a pre-existing gap that matters once cases can live only in a user list).
* `KB.kt` has favourite-specific methods (`favouriteCaseIds()`, `copyCaseAsFavourite()`, `deleteCaseFromFavourites()`); `CaseManager.ids(type)`/`all(type)` are already generic over `CaseType`.
* `PostgresCaseStore` persists `CaseType` as an **ordinal integer** (`type.ordinal` / `CaseType.entries[...]`) - `PostgresCaseStore.kt:27,101,119`. `InMemoryCaseStore` has no such dependency.
* Chat: dedicated `RuleService.copyCaseToFavourites/deleteCaseFromFavourites`, three action classes (`CopyCaseToFavourites`, `CopyCaseToFavouritesWithNewName`, `DeleteCaseFromFavourites`), an `ActionComment` reflective constructor (`server/.../kb/chat/ActionComment.kt`) that maps a JSON `action` string straight to a class of the same simple name in `io.rippledown.kb.chat.action`, a prompt section `25_favourite_cases.md`, and a `ListCapabilities` bullet.
* UI: `CaseSelector.kt` hardcodes one "Favourites" section (`favouriteCaseIds`, `FAVOURITES_SECTION_ID`/`FAVOURITES_SECTION_HEADER_ID` constants); `OpenRDRUI.kt` wires `casesInfo.favouriteCaseIds` through in three places.
* Cucumber: `FavouriteCaseListPO`/`FavouriteCaseCountPO` (fixed section ids), fixed accessors in `RippleDownUIOperator`/`LaunchedClient`/`StepsInfrastructure`, and step defs in `CaseListStepDefs.kt`/`ChatCaseDefs.kt` with no list-name parameter.
* `cucumber/.../requirements/cases/User defined case lists.feature` already replaces the old `Favourite cases.feature` (already deleted) and uses `{string}`-parameterised wording (e.g. `the "favourites" case list should contain:`), but none of its steps are bound yet, and two lines (52, 96) still use the old unquoted `the favourites case list should contain:` form - an inconsistency to fix as part of this work.
* Export/import (`KBExporter`/`KBImporter`) currently exports **only** `ProcessedCases` and `CornerstoneCases` - favourites were never exported despite `favourite_cases.md` claiming otherwise. Exporting user-defined lists is new functionality, not a rename.
## Design decisions
* Replace `CaseType` (enum) with `CaseListType`, a plain `@Serializable data class CaseListType(val name: String)` (a class, not a sealed hierarchy, so persistence/serialization stay simple: no polymorphism needed). Company object exposes the two built-ins as named instances:
    * `CaseListType.Processed` (name `"Processed Cases"`)
    * `CaseListType.Cornerstone` (name `"Cornerstone Cases"`)
    * `CaseListType.isBuiltIn` / a companion `isReserved(name)` helper (trim + case-insensitive) used to refuse copying into a built-in list.
    * Any other name is a user-defined list; it exists implicitly as soon as one case has that type, and disappears once none do (mirrors today's `favouriteCaseIds.isNotEmpty()` gating) - no separate list registry to persist.
* `CasesInfo.favouriteCaseIds` -> `CasesInfo.userDefinedCaseLists: List<CaseListInfo>`, `data class CaseListInfo(val name: String, val caseIds: List<CaseId> = emptyList())`, ordered by first-copied order (lowest case id in each group). Fix `count` to include every list so a case that only exists in a user-defined list is not hidden.
* Keep the existing "one action class per distinct JSON shape" convention, but generalise: `CopyCaseToList(listName)`, `CopyCaseToListWithNewName(listName, message)`, `DeleteCaseFromList()` (delete keeps no params, as today - the current case already carries its own list type).
* Reserved-name refusal is a server-side `IllegalArgumentException` thrown from `KB.copyCaseToList`, caught in the action's `doIt` and turned into a `ChatResponse`, following the existing pattern in `RenameAttribute.kt:27-31`. Message must contain "Cannot" and the built-in list's own name, e.g. `Cannot copy a case to "Cornerstone Cases": that is a built-in list.` (matches the feature's expected terms `Cannot`/`Cornerstone`).
* Export/import: add a third case directory `UserDefinedCases` alongside `ProcessedCases`/`CornerstoneCases`, holding every case whose type is not built-in. Each case's own serialized `CaseId.type.name` already carries its list membership, so no extra bookkeeping is needed on import - this closes the gap noted above for both old favourites and new user-defined lists.

## Stage 2: Server persistence and `KB`/`CaseManager`
* `PostgresCaseStore.kt`: change `PGCaseIds.type` from `integer(...)` to `varchar(...)` storing `CaseListType.name` directly; update `storeCaseId`/`caseId()`/`allCaseIds()` accordingly. Call out explicitly: **this is a breaking schema change** - there is no migration framework in this codebase (`SchemaUtils.create` only), so any existing local/dev Postgres database must have its `case_ids` table dropped and recreated. Update `PostgresCaseStoreTest.kt`.
* `InMemoryCaseStore.kt`: no ordinal dependency, should need no change beyond compiling against the new type - verify with its test.
* `CaseManager.kt`: keep `ids(type)`/`all(type)` (now typed on `CaseListType`); add `userDefinedListNames(): List<String>` returning distinct non-built-in type names ordered by each list's first (lowest) case id.
* `KB.kt`: replace `favouriteCaseIds()`/`copyCaseAsFavourite()`/`deleteCaseFromFavourites()` with generic equivalents:
    * `userDefinedListNames(): List<String>`
    * `casesInUserList(name: String): List<CaseId>`
    * `copyCaseToList(id: Long, listName: String, newName: String?): RDRCase` - throws `IllegalArgumentException` when `CaseListType.isReserved(listName)`.
    * `deleteCaseFromList(case: RDRCase)` - throws when `case.caseId.type.isBuiltIn`.
    * Add `allUserDefinedCases()` for Stage 6 (export).
* Update `KBTest.kt` sections covering favourites (`KBTest.kt:827-909`).
